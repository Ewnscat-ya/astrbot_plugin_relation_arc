# 关系判定方案评估决策（MIS-102）

本文件是可选任务 MIS-102 的交付物：对四个评估方向逐一给出候选方案、采用/不采用决策、行为变化、旧数据影响和回滚方案。本任务不修改任何业务代码。

基线：master `fc8092a`。评估环境：Python 3.12.10 / AstrBot 4.28.0 / SQLite 3.49.1，176/176 测试双版本通过。

---

## A. 事实归并（不同事实同分数向量 vs 同事实改写）

### 现状

`effect_signature` 将 requested delta 序列化为排序 JSON 字符串作为"签名"。`repeat_count` 的匹配逻辑：
- 有 evidence 时：按 evidence 子串匹配窗口内历史事件。
- 无 evidence 时：按签名匹配。

这意味着"谢谢你的帮助 +4"和"谢谢你的帮助 +3"（不同 delta）会生成不同签名但共享 evidence 前缀；而"帮助了我 +4"和"帮了我大忙 +4"（同 delta 不同措辞）会被视为同一事实而衰减。

### 候选方案

| 方案 | 描述 | 误判类别 | 额外成本 |
| -- | -- | -- | -- |
| 维持现状 | 向量签名 + evidence 子串 | 同事实改写（措辞不同但语义相同）被重复计分；不同事实恰好同向量被误衰减 | 零 |
| 证据指纹 | 归一化 evidence（去标点/转小写/取关键词集）后 hash | 近义改写仍可能漏匹配；跨语言不可比 | 归一化函数 + 存储 hash 字段 |
| 轻量事实归并 | 对窗口内 evidence 做关键词重叠/编辑距离 | 需要调参；中文分词引入额外依赖 | 分词库或正则规则 |

### 决策：**维持现状**

理由：
1. 误判方向是"重复计分"而非"漏计"——对用户体验的影响是分数多涨而非不涨，比反向更可接受。
2. 引入分词/编辑距离增加依赖和维护成本，且中文没有银弹分词方案。
3. `repeat_factors [1.0, 0.6, 0.3, 0.0]` 的设计本身就容忍少量重复：首轮 100%，二轮 60%，衰减足够平滑。
4. 如未来引入事实归并，建议在 `effect_signature` 层替换为语义指纹（如 embedding hash），但需先引入向量模型——超出本轮范围，拆为独立工单。

### 行为变化

无。

### 回滚

不适用（无变更）。

## B. 中性有效互动是否刷新活跃时间

### 现状

`last_interaction` 仅在 `settle_turn` 有实际分数变化（applied 非零）或绑定/安全动作时更新。纯持平聊天（模型返回 `fact_effects: []`）不触发写入，走 `zero_after_policy` 路径零落账。

### 候选方案

| 方案 | 描述 | 对衰减的影响 | 对防刷的影响 |
| -- | -- | -- | -- |
| 维持现状 | 仅分数变化才更新活跃时间 | 纯聊天用户会被衰减——这是设计意图（"不聊天就淡忘"） | 无影响 |
| 所有合法协议轮次均刷新 | 只要模型返回了有效协议块（即使 delta 全零）就 touch last_interaction | 纯聊天用户永不被衰减——衰减机制对活跃用户失效 | 增加了刷协议块的激励（虽然 stripped 后不可见） |
| 可配置开关 | 加 `touch_on_zero: bool` 配置项 | 同上但管理员可控 | 增加配置复杂度 |

### 决策：**维持现状**

理由：
1. 衰减的语义是"不聊天就淡忘"——纯持平聊天不推进关系是设计意图，不是 bug。
2. 如果改为"所有合法协议轮次都刷新"，模型只需在每轮回复一个空 `fact_effects:[]` 协议块就能永久避免衰减，等于绕过衰减机制。
3. 六维分数没有变化的"中性聊天"本身就不构成关系事件；衰减反映的是关系维度的自然淡化，与是否有消息往来无关。
4. 现有测试 `test_store_idempotency_backup_and_repeat` 和行为合同样例已覆盖此路径。

### 行为变化

无。

### 回滚

不适用（无变更）。

## C. 多人格宿主混账风险

### 现状

`identity = platform_id:sender_id`（如 `qq-adapter:user-1`），不含人格/bot 维度。scope 由 `is_global_relation` 配置决定（global 或 session）。

### 风险场景

若宿主部署了多个人格（不同 LLM persona），同一用户与多个人格交互，所有人格的结算会落入同一个 `platform:sender_id` 账户。用户与人格 A 的信赖增长会影响人格 B 的行为投影。

### 评估

| 方案 | 描述 | 迁移影响 | 复杂度 |
| -- | -- | -- | -- |
| 维持现状 | 单人格假设下无问题 | 无 | 零 |
| persona key 加入 identity | `identity = platform:persona:sender` | 需迁移所有旧数据；旧归属无法推断 | 高 |
| persona 作为 scope 维度 | 在 session scope 下按 (session_id, persona_id) 分账户 | 同上 | 中 |
| 配置开关 `persona_isolation` | 启用后 identity 追加 persona 维度 | 新旧数据并存，旧数据归"默认 persona" | 中 |

### 决策：**维持现状 + 记录风险**

理由：
1. AstrBot 当前版本（4.26–4.28）的插件框架不原生支持多人格并行——每个插件实例只服务一个 bot 人格。
2. 即使用户部署多个人格插件，每个实例有独立的 data_dir 和 store——账户数据天然隔离。
3. 仅当未来 AstrBot 支持单插件多人格并行时才需要 persona key——目前无此需求信号。
4. 贸然引入 persona 维度会破坏所有现有数据（identity 格式变更），且无法从旧数据推断人格归属。

### 行为变化

无。

### 回滚

不适用（无变更）。将来若引入 persona key，旧数据迁移策略：旧 identity 视为默认 persona，新数据按 persona 分列；提供一次性迁移脚本 + 保护备份。

## D. 结构化输出/工具通道替代标签协议

### 现状

模型在回复开头输出 `<relation_judgment>{...}</relation_judgment>` 标签块，后端用正则提取并 JSON 解析。支持 v1（仅分数）/v2（+绑定提案）/v3（+安全提案）三个 schema 版本。有窄恢复路径处理裸 JSON 泄漏。

### 候选方案

| 方案 | 描述 | 优点 | 缺点 |
| -- | -- | -- | -- |
| 维持标签协议 | 现状 | 跨模型可用（不依赖 function calling API）；已有完整的解析/剥离/恢复链路 | 模型可能格式错误、截断或泄漏 |
| Function calling / tool use | 模型通过工具调用接口提交 judgment JSON | 结构化保证、类型安全；可强制 required 字段 | 需要模型厂商支持 tool use；不同模型的 tool call 格式差异大；AstrBot 的 tool 框架是否稳定待验；多了一层抽象 |
| JSON mode | 强制模型输出纯 JSON | 解析简单 | 无法同时输出自然回复——需两次调用 |
| Structured Outputs (json_schema) | 厂商级 JSON schema 约束 | 最强保证 | 仅部分模型支持；AstrBot 框架是否透传待验证 |

### 决策：**维持标签协议**

理由：
1. 标签协议在 4.26–4.28 全版本实测通过（92→176 个测试全绿），且不受模型厂商限制。
2. AstrBot 的流式输出框架下，标签协议的剥离已在 `on_llm_response` 最终 hook 完成，早期片段泄漏的缓冲策略已有文档（HOST_COMPATIBILITY.md）。
3. Function calling 引入 AstrBot 的 tool 框架依赖，增加与宿主版本的耦合。
4. 冷启动成本：改造为 tool use 需要重写 inject（改为 tool 定义）和 judge（改为解析 tool call 返回值），同时保持 v1/v2/v3 降级兼容——工程量大但收益边际。

### 触发重评的条件

- AstrBot 发布原生 structured output 支持
- 目标模型不支持标签格式（如某些仅支持 tool use 的 API）
- 真实宿主验收发现标签协议的流式泄漏率不可接受

### 行为变化

无。

### 回滚

不适用（无变更）。

## 总结

| 方向 | 决策 | 行为变化 | 旧数据影响 | 回滚 |
| -- | -- | -- | -- | -- |
| A. 事实归并 | 维持现状 | 无 | 无 | 不适用 |
| B. 活跃时间刷新 | 维持现状 | 无 | 无 | 不适用 |
| C. 多人格混账 | 维持现状 + 记录风险 | 无 | 无 | 不适用 |
| D. 结构化输出 | 维持标签协议 | 无 | 无 | 不适用 |

**结论：四项评估均维持现状，无需代码变更。** 如未来出现触发条件（宿主多人格支持、模型协议不兼容、流式泄漏率超标），按上述分析中的重评条件重启评估，并将选定变更拆为独立实施工单。
